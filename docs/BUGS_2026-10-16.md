## BUG 1: Prefix-less model names create ghost rows in the Models registry

### Symptom
Models page shows rows that were never in any provider listing:
- `cx/gpt-5.6-luna` (provider `cx`), 2,197 requests / 130M tokens, next to the real `9dak/cx/gpt-5.6-luna` (7,904 requests / 426.8M)
- `cc/opus-55` (seen earlier by the reporter)
- `cc/zz-probe-opus` (provider `cc`), created by a test request with an invented name
- `a9dak/cc/opus99` (typo of the prefix), same path

`/v1/models` does not list them, because it aggregates live from upstream. Only the admin Models page shows them.

### Reproduction (verified live)
1. Use an API key whose model access is `all`.
2. `POST /v1/chat/completions` with `"model": "cx/gpt-5.6-luna"` (no `9dak/`). Returns 200.
3. `POST` with `"model": "cc/zz-probe-opus"` (fake). Returns 503 from 9router.
4. Models page now has both as new rows, provider `cx` and `cc`. The fake one exists even though the request failed.

A key restricted to `9dak/*` returns 403 `model_not_allowed` for bare names, which is why it only shows with unrestricted keys.

### Root cause
Registration runs on the raw request string, before the model is resolved.

1. `internal/proxy/proxy.go:320` calls `p.models.IsModelEnabled(modelName)` with the unresolved name.
2. `internal/models/models.go:94-101` (`IsModelEnabled`): when no row exists, it runs `INSERT OR IGNORE INTO models ...` with `provider_id` set to the text before the first `/`. For `cx/...` that gives `cx`, which is a 9router sub-provider, not a NineGuard provider.
3. Routing still works. `FindProviderForModel` (`internal/providers/providers.go:~517`) finds no prefix match and falls back to the default provider (9dak), so the name is forwarded upstream as-is and 9router understands `cx/`.
4. `ResolveModelID` runs later (`proxy.go:351`), too late to help.

So any string a client sends becomes a registry row, and the request is forwarded anyway.

### Impact
- **Registry pollution.** Rows with wrong `provider_id` (`cx`, `cc`, typos).
- **Split statistics.** Traffic is logged under the raw name (`proxy.go:566, 689`). `ListModels` joins on `traffic_logs.model`, and top-models uses `GROUP BY model`. So `cx/x` and `9dak/cx/x` are counted as two models.
- **Firewall bypass.** Disabling `9dak/cx/x` does not block `cx/x`. The disabled check (`proxy.go:320`) and the allow-list (`proxy.go:289`) both use the raw name, and the bare name reaches the same upstream model.
- **No validation.** Unknown or typo'd names are forwarded to 9router instead of rejected.
- Ghost rows get deleted by `applyListing` (`models.go`, orphan delete) because `cx`/`cc` match no provider, then come back on the next prefix-less request.

### Fix (v1.4.3)
Decided with the dak owner: bare names are treated as the same model, no new rows are created, unknown names are rejected, and old statistics are merged.

1. Resolve the model to its canonical ID first (`ResolveModelID`: `cx/x` becomes `9dak/cx/x`).
2. Run the allow-list, disabled check and quota on the canonical ID, so bare and prefixed forms behave the same.
3. Stop auto-inserting rows in `IsModelEnabled`. Only the sync (and the manual "Add Model") creates rows.
4. Reject unknown names, including on `all` keys, with 404 `model_not_found`. No upstream call, no new row.
5. Treat soft-removed models as known, so `removed_model_test.go` behavior is kept.
6. Safeguard: skip strict rejection for a provider that has no registered models at all (no `/models` listing). Not needed for 9dak, which has 49 listed models.
7. Log traffic under the canonical `model_id` so statistics merge.

**What was changed**
- `internal/proxy/proxy.go`: resolves the canonical ID before every model check. The key allow-list accepts the requested name or its canonical form. Unknown names get 404 `model_not_found` (logged as a 404 row, no upstream call). The disabled check runs on the canonical ID.
- `internal/models/models.go`: `IsModelEnabled` no longer inserts rows. New `HasModelsFor` is the "provider has a listing" guard. `ListModels` joins traffic on the canonical ID (case-insensitive).
- `internal/traffic/traffic.go`: removed a second auto-insert that `Record()` ran for every logged model name (this one created the ghost rows with an empty provider). Dashboard top models, error sources, distinct-model count, usage reports, last-active, the traffic model filter and the "removed" tag now use the canonical ID, falling back to the raw name for rows logged before ADR 0008.
- Tests: `internal/proxy/model_registry_test.go`, `internal/traffic/model_id_merge_test.go`, plus additions to `internal/models/lookup_test.go`.

**Known limits**
- Rows logged before ADR 0008 with a bare name and no `model_id` still group under their raw name. Merging them needs a one-off backfill, which was not written.
- The provider prefix is still matched case-sensitively (`9DAK/x` is treated as an unknown model). The model part is case-insensitive.
- A real model that the provider accepts but does not list is rejected until the sync registers it (sync runs every 30 minutes, or "Fetch from Providers"). Watch for `unknown model rejected` in the logs after deploying.
- The Traffic page model filter now matches `model_id = ? OR model = ?`, which cannot use the `model_id` index for the `OR`. Not measured on a large table.

### Test plan
Go tests in `internal/proxy` (pattern: `model_quota_proxy_test.go`, `removed_model_test.go`): a stub upstream, a `9dak`-prefixed default provider, seeded models, an unrestricted key.
- Bare `cx/x` returns 200, no new row, upstream sees `cx/x`, traffic `model_id` is `9dak/cx/x`.
- `zz-probe/cc/x` and `a9dak/cc/x` return 404, no upstream call, no row, on `all`, `custom` and `group` keys.
- Disabled `9dak/cx/x` blocks both bare and prefixed.
- Soft-removed model still reaches upstream. Empty model name skips the check.
- Unit tests: `ResolveModelID` table test, `IsModelEnabled` does not insert on unknown ID.
- After deploy, re-probe with a bare `cx/...` and a fake name, and confirm no new rows.

### Cleanup on the live instance
- Delete ghost rows: `cx/gpt-5.6-luna`, `cc/zz-probe-opus`, plus one more unidentified row (52 total minus 49 under the `9dak` filter equals 3). Filter by All Providers to find it.
- Decide whether to merge the old `cx/gpt-5.6-luna` statistics into `9dak/cx/gpt-5.6-luna`.
- Side effect of testing: about 2.5k prompt tokens on the test keys, and the two probe requests above. Rotate the two API keys used for testing.

### Open question (for the dak NineGuard owner)
Answered by the dak owner: treat bare and prefixed names as the same model, create no new model rows, and merge existing statistics. Unknown names should be rejected.
- Still worth finding out: which agents send bare names, so their config can be fixed. Traffic page, filter `cx/gpt-5.6-luna`, then look at key and IP.

## BUG 2: Cascaded NineGuard quotas and `/quota` are not grouped by sub-provider

**Status: root cause confirmed. The dak instance runs an older build. The fix is already in this repo (`9a1c259`) and needs to be deployed. No code change is needed for the main symptom.**

### Symptom
The "nineguard kantor" cascaded provider (Upstream Quotas page) and the `/quota` chat command show one flat list under `nineguard kantor · 9router DAK`. Buckets from different sub-providers are mixed:
- Claude Code: `Session (5h)`, `Weekly (7d)`, `Weekly Fable (7d)`
- prolite: `5h Session`
- Antigravity: `Claude & GPT (5h)`, `Gemini (5h)`, `Claude & GPT (Weekly)`, `Gemini (Weekly)`, `Gemini 3.1 Flash Image`

The 9router provider page on the dak instance itself shows one card per account with its plan (`Claude Code`, `prolite`, `Antigravity`). The outer instance doesn't.

### Evidence
1. `GET https://nineguard.prodak.id/v1/quota` (inner instance) returns exactly one pool:
   ```
   upstream_pools: [ { provider: "9router DAK", family: "9router DAK",
                       buckets: [ ...all buckets of all accounts in one list... ] } ]
   ```
   There is no `sub_provider` field and no `" · <sub>"` in `family`.
2. The dak instance footer shows build **`d733b9a`**. That is `Merge pull request #5 from DarkTama/main` on the fork `aribrilliantsyah/nineguard`. It sits on `53102ff` (**v1.4.1**).
3. At `d733b9a`, `internal/upstream/pool.go` has `MergeAccountPools(...) *MergedPoolQuota`, which returns a **single** merged pool. It has no `resolveSubProvider` and no per-sub-provider grouping. That is the flat output above.
4. This repo's `main` is two commits ahead of `d733b9a`:
   - `9a1c259` "sub-provider quota grouping, cascaded tag propagation ... bump to v1.4.2". `MergeAccountPools` now returns `[]MergedPoolQuota`, one per sub-provider, with `SubProvider` set and `Family` like `9router DAK · Anthropic`.
   - `19adcc3` "raise quota refresh timeouts, add 9router cache fallback, preserve stale buckets on error".

### Why the outer instance shows a flat list
The loss happens before the outer instance sees the data. The inner `/v1/quota` answer has one group, so there is nothing to split:
- `internal/upstream/nineguard.go:165-179` uses `pool.SubProvider`, then the text after `" · "` in `pool.Family`, then falls back to `pool.Provider`. Here all are empty or absent, so it ends up with `9router DAK`.
- `MergeAccountPools` then builds the family `nineguard kantor · 9router DAK`. That is what both screenshots show.

### Resolution
1. Get this repo's `main` (or at least `9a1c259` and `19adcc3`) into the fork `aribrilliantsyah/nineguard`. Local remotes: `origin` is `DarkTama/nineguard`, and `upstream` is the fork. Fork `main` was last synced via PR #5, so a new PR from `DarkTama/main` is the same route.
2. Rebuild and redeploy the **inner dak instance first**. The sub-provider fields come from it.
3. Redeploy the outer instance too if it is older than v1.4.2. Its cascaded adapter (`nineguard.go`) needs to read `sub_provider` from the inner response.
4. Verify after deploy: `GET /v1/quota` on the inner instance should return several `upstream_pools` with `sub_provider` set (for example `9router DAK · Anthropic`, `9router DAK · Antigravity`). The outer Upstream Quotas page and `/quota` should then group the same way.

### Not yet verified
- Whether current `main` groups the **real** 9router data from this deployment correctly. The commit has unit tests (`pool_test.go`), but I haven't run it against the dak instance's connection payload. In particular, `resolveSubProvider` takes the key from `conn.Provider`, then `conn.Plan`, then the `" · "` part of `AccountLabel`. The screenshots show plans named `Claude Code`, `prolite` and `Antigravity`. If 9router returns an empty `provider` for some connections, and the plan is `"Shared Upstream Pool"` or contains "budget", those connections would fall into one empty-key group. Check this right after deploying.
- The inner instance's account names are redacted in the screenshots, so I couldn't compare them.

### Follow-up test (optional hardening, in this repo)
- Add a cascaded-payload test in `internal/upstream` with distinct `sub_provider` values and assert they stay separate end to end through the outer `MergeAccountPools` and `FormatQuotaMarkdown`.
- Consider showing a note on the outer side when an inner pool has no sub-provider but its bucket names suggest several families. That would make a version mismatch visible instead of silently flattening.

### Secondary observations (cosmetic)
- The outer "Key Allowance" row renders as `nineguard kantor · Nineguard` in `/quota`, because the synthesized connection uses `Provider: "nineguard"` (`nineguard.go:~118`).
- The cascaded Key Allowance bucket reads `9dak/cc/claude-opus-5-5 (weekly)`, the inner instance's canonical model ID. It matches only because the key was configured with the prefixed name (see BUG 1).
