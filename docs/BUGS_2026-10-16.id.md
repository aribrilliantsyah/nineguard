## BUG 1: Request tanpa prefix membuat baris model "hantu" di daftar Models

### Gejala (sesuai laporan Kang di WhatsApp)
Di halaman Models muncul baris yang tidak pernah ada di daftar provider:
- `cx/gpt-5.6-luna` (provider `cx`), 2.197 request / 130M token, di samping baris asli `9dak/cx/gpt-5.6-luna` (7.904 request / 426,8M token)
- `cc/opus-55`, padahal model sebenarnya `9dak/cc/opus99`
- `cc/zz-probe-opus`, dibuat oleh request tes saya dengan nama karangan
- `a9dak/cc/opus99` (salah ketik prefix) akan jalur yang sama

`/v1/models` tidak menampilkannya, karena endpoint itu mengambil daftar langsung dari upstream. Hanya halaman admin Models yang menampilkannya. Perhatikan filter provider: kalau terpilih `9router DAK (9dak)`, baris hantu tersembunyi (49 dari 52 model). Pilih **All Providers** untuk melihatnya.

### Skenario yang kemungkinan terjadi
1. Ada agent atau client yang config modelnya `cx/gpt-5.6-luna` atau `cc/opus-55`, tanpa `9dak/` di depannya. Itu nama yang dikenal 9router sendiri (`cx` = Codex, `cc` = Claude Code), jadi si pembuat config merasa itu benar.
2. Request masuk ke dak NineGuard dengan API key yang akses modelnya `all`, atau pola yang meloloskan nama itu.
3. NineGuard tidak menemukan prefix provider di depan nama (`9dak/`), lalu **memakai provider default** (9router DAK) dan meneruskan nama apa adanya ke 9router. 9router paham `cx/...`, jadi request **berhasil**. Itu sebabnya tidak ada yang sadar: dari sisi pemakai semuanya jalan.
4. Tetapi sebelum meneruskan, NineGuard mengecek "apakah model ini diblokir?" memakai nama mentah dari client. Karena baris untuk `cx/gpt-5.6-luna` tidak ada, NineGuard **otomatis membuatnya** dengan `provider = teks sebelum "/" pertama` (`cx`). Provider `cx` itu salah, karena `cx` hanya sub-provider milik 9router, bukan provider di NineGuard.
5. Hasilnya: baris hantu muncul, statistik model yang sama terpecah dua (`cx/...` dan `9dak/cx/...`), dan setiap request berikutnya menambah hitungan baris hantu itu.
6. Baris hantu kadang hilang sendiri: proses sync (tiap 30 menit atau tombol "Fetch from Providers") menghapus baris yang provider-nya tidak cocok dengan provider mana pun (`cx`, `cc`). Lalu muncul lagi saat ada request tanpa prefix berikutnya. Itu cocok dengan cerita bahwa `cc/opus-55` pernah muncul, lalu hilang.

### Lokasi di kode
| Langkah | Berkas |
|---|---|
| Pengecekan memakai nama mentah dari client | `internal/proxy/proxy.go:320` (`IsModelEnabled(modelName)`) |
| Pembuatan baris otomatis | `internal/models/models.go:94-101` (`INSERT OR IGNORE INTO models ...`) |
| Fallback ke provider default saat tidak ada prefix | `internal/providers/providers.go:~517` (`FindProviderForModel`) |
| Nama kanonik baru dihitung setelahnya, terlambat | `internal/proxy/proxy.go:351` (`ResolveModelID`) |
| Pengecekan izin API key juga memakai nama mentah | `internal/proxy/proxy.go:289` |
| Daftar Models menggabungkan traffic dengan nama mentah | `internal/models/models.go` (`LEFT JOIN traffic_logs t ON m.id = t.model`) |

### Dampak
- **Daftar model tercemar** oleh baris dengan provider salah (`cx`, `cc`, salah ketik).
- **Statistik terpecah**: model yang sama dihitung sebagai dua model di halaman Models.
- **Firewall bisa dilewati**: kalau admin menekan *Disable* pada `9dak/cx/gpt-5.6-luna`, request ke `cx/gpt-5.6-luna` tetap lolos, padahal sampai ke model upstream yang sama. Ini yang paling serius untuk kontrol akses.
- **Tidak ada validasi nama**: nama ngawur atau salah ketik tetap diteruskan ke 9router, dan tetap dicatat sebagai baris model.
- Key yang dibatasi (misal `9dak/*`) justru kena 403 untuk nama tanpa prefix, jadi perilakunya tidak konsisten antar key.

### Bukti yang sudah diverifikasi
1. **Instance dak, key mode `all`:**
   - `cx/gpt-5.6-luna` (tanpa prefix) mengembalikan **200**, request berhasil.
   - `cc/zz-probe-opus` (nama karangan) mengembalikan **503** dari 9router, tapi barisnya **tetap terbentuk** di halaman Models dengan provider `cc`.
2. **Screenshot halaman Models** menunjukkan baris `cx/gpt-5.6-luna` (provider `cx`, 2.197 request, "just now") dan `cc/zz-probe-opus` (provider `cc`, 2 request, "1m ago"). Baris kedua hanya bisa muncul dari request tes saya, jadi itu bukti paling bersih.
3. **Key `Eka`** (dibatasi) mendapat 403 `model_not_allowed` untuk nama tanpa prefix, jadi key terbatas tidak bisa memicu bug. Bug hanya muncul di key akses `all`.
4. **Tes otomatis** (`internal/proxy/model_registry_test.go`, DB sementara dan upstream palsu, tidak menyentuh server) gagal di kode sekarang:
   - `ghost row "cx/gpt-5.6-luna" was auto-registered`
   - `cx/gpt-5.6-luna: want 403 model_disabled, got 200` (firewall bypass)
   - 4 nama karangan semuanya mengembalikan 200, bukan 404.

### Cara memastikan sendiri (aman)
**A. Jalankan tes lokal (tanpa server nyata):**
```
go test ./internal/proxy/ -run 'TestBareSubProviderModelCreatesNoGhostRow|TestDisabledModelCannotBeBypassedWithBareName' -v
```

**B. Di instance dak, dengan key akses `all`:**
```
curl -s https://nineguard.prodak.id/v1/chat/completions \
  -H "Authorization: Bearer <key-akses-all>" -H "Content-Type: application/json" \
  -d '{"model":"cc/tes-123","messages":[{"role":"user","content":"hi"}]}'
```
Requestnya gagal (503), itu wajar. Lalu buka **Models & Groups**, pilih **All Providers**, cari `tes-123`. Kalau muncul baris `cc/tes-123` dengan provider `cc`, bug terbukti. Hapus barisnya setelah itu.

**C. Cek di Traffic**: filter model `cx/gpt-5.6-luna`, lihat key dan IP client mana yang mengirim tanpa prefix. Itu agent yang config-nya perlu diperbaiki.

### Perbaikan (v1.4.3)
Disepakati dengan pemilik dak NineGuard: nama tanpa prefix dianggap model yang sama, tidak membuat baris baru, nama yang tidak dikenal ditolak, dan statistik lama digabung.

1. **Resolve dulu**: ubah `cx/gpt-5.6-luna` menjadi `9dak/cx/gpt-5.6-luna` sebelum semua pengecekan (izin key, disabled, quota). Bentuk tanpa prefix dan berprefix diperlakukan sebagai model yang sama, dan celah firewall tertutup.
2. **Jangan buat baris otomatis** di `IsModelEnabled`. Baris hanya dibuat oleh sync dan tombol "Add Model".
3. **Tolak nama yang tidak dikenal** dengan 404 `model_not_found`, termasuk untuk key `all`. Model yang di-soft-remove tetap dianggap dikenal, dan provider yang belum punya daftar model dilewati dari pengecekan ketat.
4. **Gabungkan statistik** di daftar Models (join ke `model_id` kanonik).
5. **Nama tanpa prefix tetap dilayani sebagai alias** (dihitung di baris kanonik, tidak didaftarkan), dengan log peringatan supaya agent yang salah config bisa ditemukan dan dibenahi.
6. Soal usulan Kang: nama yang tersedia untuk API key terpisah dari nama yang dikirim ke upstream. Secara konsep, kode sudah punya dua nama itu secara implisit: nama kanonik (`9dak/cx/...`) dan nama upstream (`cx/...`). Kolom `upstream_name` eksplisit baru berguna kalau butuh rename atau alias di luar sekadar membuang prefix. Saya sarankan itu langkah kedua, bukan bagian dari perbaikan bug ini.

**Yang diubah**
- `internal/proxy/proxy.go`: menentukan ID kanonik sebelum semua pengecekan model. Izin key menerima nama yang diminta atau bentuk kanoniknya. Nama tidak dikenal mendapat 404 `model_not_found` (dicatat sebagai baris 404, tidak diteruskan ke upstream). Pengecekan disabled memakai ID kanonik.
- `internal/models/models.go`: `IsModelEnabled` tidak lagi membuat baris. `HasModelsFor` baru, sebagai pengaman "provider punya daftar model". `ListModels` menggabungkan traffic lewat ID kanonik (tidak peka huruf besar/kecil).
- `internal/traffic/traffic.go`: menghapus auto-insert kedua yang dijalankan `Record()` untuk setiap nama model yang dicatat (yang ini yang membuat baris hantu dengan provider kosong). Top models dashboard, sumber error, jumlah model unik, laporan penggunaan, last-active, filter model di Traffic, dan tag "removed" sekarang memakai ID kanonik, dengan fallback ke nama mentah untuk baris sebelum ADR 0008.
- Tes: `internal/proxy/model_registry_test.go`, `internal/traffic/model_id_merge_test.go`, dan tambahan di `internal/models/lookup_test.go`.

**Batasan yang masih ada**
- Baris sebelum ADR 0008 dengan nama tanpa prefix dan tanpa `model_id` tetap dikelompokkan dengan nama mentahnya. Menggabungkannya butuh backfill sekali jalan, dan itu belum dibuat.
- Prefix provider masih dicocokkan peka huruf besar/kecil (`9DAK/x` dianggap model tidak dikenal). Bagian nama modelnya tidak peka.
- Model asli yang diterima provider tapi tidak ada di daftarnya akan ditolak sampai sync mendaftarkannya (sync tiap 30 menit, atau "Fetch from Providers"). Pantau log `unknown model rejected` setelah deploy.
- Filter model di halaman Traffic sekarang memakai `model_id = ? OR model = ?`, yang tidak bisa memakai index `model_id` untuk bagian `OR`. Belum diukur di tabel besar.

### Risiko yang perlu dipertimbangkan
- Menolak nama yang tidak dikenal bisa memutus agent yang selama ini memakai nama yang diterima 9router tapi tidak ada di daftar sync. Daftar dak lengkap (49 model), jadi risikonya kecil, tapi belum bisa dipastikan. Opsi bertahap: tahap pertama hanya mencatat log nama yang tidak dikenal tanpa menolak.
- 2.197 request lama di `cx/gpt-5.6-luna` tetap jadi riwayat, kecuali digabung manual.

### Pembersihan di instance yang berjalan
- Hapus baris hantu: `cx/gpt-5.6-luna`, `cc/zz-probe-opus`, dan satu baris lain yang belum teridentifikasi (52 total dikurangi 49 di filter `9dak` sama dengan 3). Gunakan All Providers untuk mencarinya.
- Putuskan apakah statistik lama `cx/gpt-5.6-luna` perlu digabung ke `9dak/cx/gpt-5.6-luna`.
- Efek samping tes saya: sekitar 2,5 ribu token prompt di key tes, dan dua request di atas. Mohon rotasi kedua API key yang dipakai untuk tes, karena sudah tertulis di chat.

### Pertanyaan untuk pemilik dak NineGuard
Sudah dijawab pemilik dak: nama tanpa prefix dan berprefix dianggap model yang sama, tidak membuat baris model baru, statistik lama digabung. Nama yang tidak dikenal ditolak.

Masih perlu dicari tahu: agent mana yang mengirim nama tanpa prefix, supaya config-nya dibenahi. Di halaman Traffic, filter `cx/gpt-5.6-luna`, lalu lihat key dan IP-nya.

## BUG 2: Quota cascaded dan `/quota` tidak dikelompokkan per sub-provider

**Status: penyebab terkonfirmasi, build yang ter-deploy di dak lebih lama. Perbaikannya sudah ada di repo ini (`9a1c259`) dan tinggal di-deploy.**

### Gejala
Halaman Upstream Quotas milik provider "nineguard kantor" dan perintah `/quota` menampilkan satu daftar datar dengan judul `nineguard kantor · 9router DAK`. Bucket dari sub-provider berbeda tercampur:
- Claude Code: `Session (5h)`, `Weekly (7d)`, `Weekly Fable (7d)`
- prolite: `5h Session`
- Antigravity: `Claude & GPT (5h)`, `Gemini (5h)`, `Claude & GPT (Weekly)`, `Gemini (Weekly)`, `Gemini 3.1 Flash Image`

Di halaman provider 9router pada instance dak sendiri, kartunya terpisah per akun dengan planmya (`Claude Code`, `prolite`, `Antigravity`). Di instance cascaded tidak.

### Skenario yang terjadi
1. Instance kantor (cascaded) menarik kuota dari endpoint `/v1/quota` milik instance dak.
2. Instance dak menjawab dengan **satu pool saja**: `provider: "9router DAK"`, `family: "9router DAK"`, tanpa `sub_provider`, berisi semua bucket semua akun dalam satu daftar.
3. Instance kantor tidak punya apa-apa untuk dipisah, karena info sub-provider sudah hilang di sisi dak. Ia memakai nama provider sebagai gantinya, jadi tampil `nineguard kantor · 9router DAK`.
4. Penyebab di sisi dak: build `d733b9a` (v1.4.1) memakai versi lama `MergeAccountPools` yang mengembalikan **satu** pool gabungan, tanpa pengelompokan per sub-provider.
5. Pengelompokan per sub-provider baru ditambahkan di commit `9a1c259` (v1.4.2), dan commit itu belum ada di build dak.

### Bukti
1. `GET https://nineguard.prodak.id/v1/quota` mengembalikan tepat satu pool tanpa `sub_provider`.
2. Footer dak NineGuard menampilkan build `d733b9a`, yaitu `Merge pull request #5 from DarkTama/main` di fork, di atas `53102ff` (v1.4.1).
3. Di `d733b9a`, `internal/upstream/pool.go` punya `MergeAccountPools(...) *MergedPoolQuota` (satu pool). Di repo ini, fungsi itu mengembalikan `[]MergedPoolQuota` (satu per sub-provider, dengan `SubProvider` terisi).
4. Repo ini dua commit lebih maju dari dak: `9a1c259` (pengelompokan sub-provider) dan `19adcc3` (timeout, fallback cache 9router).

### Cara memperbaiki
1. Masukkan `main` repo ini (minimal `9a1c259` dan `19adcc3`) ke fork `aribrilliantsyah/nineguard`, lewat PR seperti PR #5.
2. Build dan deploy ulang **instance dak dulu**, karena field sub-provider datang darinya.
3. Deploy ulang instance kantor juga kalau versinya di bawah v1.4.2.
4. Verifikasi: `GET /v1/quota` di dak harus mengembalikan beberapa `upstream_pools` dengan `sub_provider` terisi (misal `9router DAK · Anthropic`, `9router DAK · Antigravity`). Halaman Upstream Quotas dan `/quota` di kantor harus ikut terkelompok.

### Belum terverifikasi
- Apakah `main` sekarang mengelompokkan data 9router **asli** dengan benar. Ada tes unit, tapi belum dijalankan terhadap data koneksi dak. Kalau 9router mengembalikan `provider` kosong untuk sebagian koneksi dan plannya `"Shared Upstream Pool"` atau mengandung "budget", koneksi itu bisa masuk satu grup. Cek segera setelah deploy.
- Nama akun di screenshot di-blur, jadi tidak bisa dibandingkan.

### Catatan kecil (kosmetik)
- Baris "Key Allowance" di `/quota` kantor tampil sebagai `nineguard kantor · Nineguard`.
- Bucket Key Allowance memakai ID model kanonik (`9dak/cc/claude-opus-5-5`), yang cocok hanya karena key diatur dengan nama berprefix (lihat Bug 1).
